# LogSentinel

Небольшая система обнаружения атак по логам: читает access-лог nginx и лог sshd, находит подозрительную
активность по правилам, сохраняет алерты и строит отчёт. Работает как «мини-SIEM» для одного сервера.

Проект учебный. Я делал его как вторую часть связки с [InvoiceShield](https://github.com/KIRILL242183/InvoiceShield):
InvoiceShield — приложение, а LogSentinel смотрит, что с ним пытаются сделать из сети. Настоящий SIEM он не заменяет
(см. «Ограничения»).

Зависимостей, кроме стандартной библиотеки Python, нет. Нужен Python 3.11+.

## Что умеет

- Разбирает логи nginx (формат `combined`) и sshd (классический syslog, вывод `journalctl` и ISO-время),
  в том числе старые сжатые логи после logrotate (`access.log.2.gz`).
- 8 правил, у каждого есть техника из MITRE ATT&CK (таблица ниже, подробности в [docs/RULES.md](docs/RULES.md)).
- Считает окна по времени из самих логов, а не по часам компьютера, поэтому один и тот же лог всегда даёт один результат.
- Объединяет повторы: долгий перебор пароля даёт один алерт со счётчиком, а не тысячи строк.
- Список доверенных адресов, который не анализируется.
- Режимы: `analyze` (готовые логи), `follow` (как `tail -f`, с учётом ротации логов), `simulate`, `blocklist`.
- Вывод: консоль, JSON Lines, SQLite, отчёт в Markdown, уведомления в Telegram.
- Код возврата `--fail-on` для использования в CI.

| Правило | Что ловит | MITRE ATT&CK |
|---|---|---|
| SSH-BRUTE-FORCE | серия неудачных паролей с одного IP | T1110.001 |
| SSH-USER-ENUM | много разных имён пользователей с одного IP | T1110.003 |
| SSH-SUCCESS-AFTER-FAILS | успешный вход сразу после серии неудач | T1110, T1078 |
| WEB-LOGIN-BRUTE-FORCE | много неудачных POST на `/login` | T1110.001 |
| WEB-SCANNER | много разных 404/403 за минуту | T1595.003 |
| WEB-ATTACK-PATTERN | SQLi, XSS, path traversal, Log4Shell и другие сигнатуры в адресе | T1190 |
| WEB-SCANNER-UA | User-Agent sqlmap, nikto, nmap и подобных | T1595.002 |
| WEB-SENSITIVE-PATH | запросы к `/.env`, `/.git`, `/phpmyadmin` и т. п. | T1595.003 |

## Быстрый старт

```bash
git clone https://github.com/KIRILL242183/logsentinel.git
cd logsentinel
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
pytest
```

Создать учебные логи с «атаками» и разобрать их:

```bash
logsentinel simulate --out demo
logsentinel analyze --nginx demo/access.log --ssh demo/auth.log --year 2026 --report demo/report.md --db demo/alerts.db
```

Результат на этих логах (524 строки):

```

[CRITICAL] 2026-11-04 10:00:00Z 203.0.113.77    SSH-SUCCESS-AFTER-FAILS (T1110, T1078) Успешный вход SSH после серии неудач

[MEDIUM  ] 2026-11-04 10:23:30Z 203.0.113.200   WEB-SENSITIVE-PATH x13 (T1595.003) Попытка открыть служебные файлы и админки
```

`xN` — сколько раз правило сработало на этот IP; повторы внутри 5 минут объединяются в один алерт.
Нормальные пользователи (в том числе тот, кто дважды ошибся паролем) алертов не вызывают, это проверяется тестом.

Слежение за живыми логами и уведомления в Telegram:

```bash
export TELEGRAM_TOKEN=...      # токен бота
export TELEGRAM_CHAT_ID=...
logsentinel follow --nginx /var/log/nginx/access.log --ssh /var/log/auth.log --telegram
```

Список IP для nginx из сохранённых алертов (перед применением его надо проверить вручную):

```bash
logsentinel blocklist --db demo/alerts.db --format nginx > blocklist.conf
```

## Настройка

Пороги меняются в TOML-файле, пример: [config.example.toml](config.example.toml).
Опечатка в имени параметра даёт ошибку, а не молча игнорируется.

```bash
logsentinel analyze --config config.example.toml --nginx access.log
```

## Как это связано с InvoiceShield

InvoiceShield при неверном пароле отвечает `200` со страницей ошибки, а при верном — `303`.
Поэтому правило WEB-LOGIN-BRUTE-FORCE считает `POST /login` со статусом 200 неудачей. Если ответ `429`, значит,
сработал собственный лимит попыток в приложении; такие запросы тоже попадают в счётчик, а в алерте указано, сколько их было.
Если запускать приложение за nginx, адрес клиента нужно брать из заголовков прокси, иначе в логах будет адрес самого nginx
(как это настроено, описано в проекте `invoiceshield-infra`).

## Тесты

```bash
pytest          # 64 теста, меньше секунды
ruff check .
```

Тесты проверяют разбор строк (в том числе мусорные), каждое правило на «срабатывает» и «не срабатывает»,
объединение повторов, список доверенных адресов, чтение файла при ротации и недописанной строке,
а также сквозной сценарий: сгенерированные логи должны дать ровно те алерты, что записаны в `logsentinel/simulate.py`.

## Структура

```
logsentinel/
  parsers.py   разбор строк nginx и sshd
  rules.py     правила и скользящее окно
  engine.py    прогон событий через правила, объединение повторов
  storage.py   SQLite
  sinks.py     консоль, JSON Lines, Telegram
  follow.py    чтение растущего файла
  report.py    отчёт Markdown
  simulate.py  генератор учебных логов
  cli.py       командная строка
docs/          описание правил и архитектуры
tests/
```

## Ограничения

- Правила работают по порогам и сигнатурам. Медленный перебор (одна попытка в несколько минут) и атака с
  множества адресов сразу порогов не достигают.
- Сигнатуры атак — простые регулярные выражения, они дают ложные срабатывания и обходятся кодированием.
  Алерт говорит «запрос похож на атаку», а не «атака удалась»; ответ сервера указан в `details` для проверки вручную.
- Не обрабатываются тела POST-запросов и заголовки, кроме `User-Agent`, потому что их нет в стандартном логе nginx.
- Логи читаются как есть: если злоумышленник получил доступ к серверу, он может их изменить. Для серьёзного применения
  логи нужно сразу отправлять на отдельный сервер.
- Проверено на сгенерированных логах и на синтетических строках в тестах, на реальном внешнем трафике не проверялось.
- Автоматической блокировки нет специально: список адресов надо смотреть глазами.
